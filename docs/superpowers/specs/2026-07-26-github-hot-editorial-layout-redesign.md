# GitHub 热门双 Skill 编辑与微信排版重设计

## 背景

现有 GitHub schema v2 已经能够保存核验、许可证、维护、风险和图片授权信息，但生成的读者正文过度轻量，呈现为结构正确的审核报告，而不是值得阅读和收藏的微信公众号文章。单项目测试 fixture 进一步放大了标题机械、导语空泛、项目卡缺少编辑表达、视觉节奏不足和结尾模板化等问题。

本设计只重做 `github-hot-research` 与 `wechat-content` 的 GitHub 热门链路。“昨日大事”已经定型，其内容、标题和视觉行为不得改变。两个 Skill 必须自包含；可以吸收 `wechat-article-writer` 的写作与排版原则，但运行时不得读取、调用或依赖该 Skill。

## 目标

- 发现执行时刻前连续 7 天内真正出现热度变化或突然爆火的 GitHub 项目。
- 生成有吸引力的动态标题、开头、项目介绍和有余味的结尾。
- 使用适合微信手机阅读的单栏编辑卡片式排版。
- 保留完整审核能力，但不把许可证、核验和内部风险负担转嫁给读者。
- 保持栏目模块隔离，为以后新增 `AI 新发现`、`实用工具` 等类型提供清晰扩展边界。
- 只生成本地审核包，不上传、不创建公众号草稿、不发布。

## 非目标

- 不修改 `daily-news` 的研究规则。
- 不修改 `wechat-content` 的“昨日大事”正文、标题和视觉主题。
- 不引入 `wechat-article-writer` 运行时依赖。
- 不将 GitHub 热门扩展为单项目深度评测或个人实测文章。
- 不虚构运营者观点、使用经历或项目热度原因。

## 双 Skill 职责

### `github-hot-research`

研究层回答“本周什么项目真的火了，以及为什么值得写”：

- 发现 12—20 个本周候选，至少深度核验 8 个。
- 默认入选 5 个，允许 5—7 个。
- 保存本周热度证据、爆火原因、用途、具体场景、三个可读亮点、适合人群、上手条件和图片候选。
- 保存 README、许可证、维护、动态指标、风险、证据、完整候选及未入选原因。
- 提供支持动态标题、开头、项目过渡和结尾的本期编辑线索。
- 输出平台无关内容包，不生成微信 Markdown、HTML、封面或正文图。

### `wechat-content`

制作层回答“怎样把核验后的研究内容变成值得读的微信文章”：

- 按 `content_type` 加载独立栏目模块。
- 只对 `github-hot` 使用本设计；`daily-news` 保持现状。
- 基于研究包证据生成标题、开头、项目段落、过渡和结尾。
- 生成手机单栏、内联样式 HTML、一键复制、封面、总览图、项目图、结尾图和审核台。
- 完整审核信息位于复制区外。
- 样式、模板、配色和图片降级能力全部内置。

## 一周热门与爆火定义

研究窗口固定为执行时刻前连续 7 天。长期高 Star 不能自动等同于本周热门。

候选信号分三层：

1. GitHub 内部信号：Trending、Explore、Star 变化、Fork、Issue、Release 和 Commit。
2. 外部传播信号：Hacker News、Reddit、开发者社区、技术媒体或项目官方发布。
3. 热度归因：首次发布、重大版本、功能变化、教程传播、社区事件或无法确认。

Trending 和外部讨论只用于发现与交叉印证；用途、版本、维护、许可证等事实必须回到项目官方页面核验。

选择约束：

- 优先本周新爆款。
- 重新走红的成熟项目最多 2 个。
- AI 项目最多 3 个。
- 同类项目最多 3 个。
- 最近 8 期已出现且没有重大变化的项目排除。
- 不足 5 个合格项目时宁可减少，不用普通高 Star 项目凑数，并将状态设为 `needs_review`。
- `weekly_stars` 无法可靠确认时使用 `null`，正文省略该标签，不写 0。

明显安全争议、用途不清、真实性无法核验，或需要高权限但官方缺少合理说明的项目不得进入正文。

## 研究内容包编辑字段

研究包继续保留事实与审核字段，并新增或明确以下平台无关编辑材料：

- `weekly_theme`：本期确有证据支撑的共同变化；不存在时为空。
- `theme_evidence`：支持共同变化判断的项目、事实和来源。
- `editorial_angles`：本期可用的标题和导语角度，不是成品微信文案。
- `closing_observations`：由本期项目共同支持的收束观察。
- 每项 `hot_reason`：为什么在本周受到关注及对应证据。
- 每项 `use_case`：读者能够理解的具体问题与使用场景。
- 每项 `editorial_summary`：80—120 字的项目价值说明。
- 每项三个具体、可核验的 `highlights`。
- 每项 `audience` 和 `requirements`，用于形成“适合谁”和“上手条件”。

事实字段与编辑字段必须分离。编辑判断必须能回指本期证据，不能从项目名称或类别自由推断。

## 动态文章结构

### 标题

标题必须概括本期实际变化或项目价值，不使用“本周 GitHub 热门：5 个项目”一类包标题。标题克制、有信息量，不使用“震惊”“颠覆”“不看后悔”等夸张表达。

### 开头

开头由三部分组成：

1. 本周共同变化或多条不同路线。
2. 本期筛选给读者带来的价值。
3. 一句克制的栏目表达。

有共同趋势时使用主题型开头。没有共同趋势时明确写成“本周值得关注的几条不同路线”，不得硬凑主题。结构保持稳定，具体句子每期动态生成。

### 单项目段落

采用已确认的“编辑卡片式”单栏结构：

1. 项目编号与类别。
2. 项目名称和一句准确说明。
3. “为什么这周火”。
4. 80—120 字“它能帮你做什么”的编辑解读。
5. 一张官方真实图片、用途示意图或本地视觉。
6. 语言、Star、可用时的本周新增、Fork 数据标签。
7. 深色“一句话推荐”信息块。
8. 三个具体、可核验的亮点。
9. “适合谁”和客观上手条件。
10. GitHub 官方地址。

正文不显示许可证状态、核验时间、维护证据、授权边界、淘汰原因或内部风险。Python、API Key、本地部署、显卡等直接影响上手的条件可以自然展示。

### 结尾

结尾必须回看本期项目共同体现的变化，区分短期热度与长期价值，并用一句有记忆点但不过度煽情的栏目表达收束。没有共同趋势时不做宏大判断。

标题、开头和结尾必须随每期内容变化：

- 不连续复用同一段落。
- 禁止固定套用“过去一周”和“看完这一周”等句式。
- 不得生成研究包证据不支持的趋势判断。
- 不得虚构个人体验、喜好或运营者观点。

## 视觉与配色

视觉采用“真实项目优先、统一编辑包装”：

- 封面根据本期主题生成独立视觉。
- 总览图表达 5—7 个项目的用途关系，而不是纯装饰。
- 项目图优先使用来源、用途和授权均已核验的官方截图、演示图或架构图。
- 官方图不可用时使用基于已核验用途的 Image2 示意图。
- Image2 不可用时使用高质量本地项目视觉，不使用空白几何占位图。
- 图片图注只说明“项目官方资料”或“项目用途示意”等读者信息；图片授权审核留在复制区外。

配色采用“品牌稳定、主题半动态”：

- 深蓝品牌主色、字体层级、版心、间距、项目编号和卡片形态保持稳定。
- 封面背景、强调色、数据标签和少量装饰色根据本期主题选择。
- AI 与自动化可用深蓝加电光青；开发工具与基础设施用海军蓝加青绿；创意工具用深蓝加暖橙；数据、安全与系统工具用石墨蓝加琥珀黄；主题分散时使用深蓝加地图绿。
- 配色选择由规则决定并写入 `render-manifest.json`，相同内容包重复生成必须一致。

## 复制区与审核台

读者复制区只包含可直接阅读的文章、正文图和自然上手条件。

复制区外审核台保留：

- README、许可证、Commit、Release 和维护核验。
- 动态指标核验时间。
- 全部风险与证据。
- 候选池、未入选项目和淘汰原因。
- 图片来源、授权和实际降级模式。
- 标题、开头和结尾所依据的主题证据。

复制成功不等于发布就绪。`needs_review` 可以在读者字段完整时复制排版，但审核台必须明确不能直接发布。

## 降级与错误处理

- 缺少共同趋势：使用多路线结构。
- 缺少周增 Star：省略标签。
- 缺少合格官方图：降级到 Image2，再降级到本地视觉。
- 缺少单项必要编辑材料：状态变为 `needs_review`，不得输出占位符。
- 入选少于 5 个：允许减少，状态变为 `needs_review`。
- 存在明显安全问题：项目不入选，不依赖正文警告弥补研究缺陷。
- 任何降级必须写入审核台和 `render-manifest.json`，不得对读者伪称官方图或实时生成图。

## 模块边界

`wechat-content` 的 GitHub 文章构建、主题选择、图片选择和审核台应放在独立 GitHub 栏目模块中。共享层只负责内容包分派、文件输出、通用微信复制和封面尺寸。不得继续把 GitHub 与新闻分支堆叠在单个大型渲染函数中。

新增内容类型时必须提供独立栏目规范、构建器、视觉规则、fixture 和回归测试，不得修改其他栏目行为。

## 测试与验收

严格测试优先。至少覆盖：

- 7 天时间窗与本周热度证据。
- 新爆款优先、成熟项目最多 2 个。
- AI、同类和历史重复上限。
- 动态指标与 `weekly_stars: null`。
- 研究包主题、热度原因和编辑摘要均有证据。
- 标题、开头、项目解读和结尾只使用本期材料。
- 连续两期不复用相同开头和结尾。
- 无共同主题时正确降级。
- 正文不出现许可证、内部风险和审核字段。
- 上手条件保持客观准确。
- 每个项目恰好有一张正文图。
- 官方图、Image2 和本地视觉的优先级与图注正确。
- 主题配色确定且可复现。
- 复制区结构、内联样式和图片完整。
- 5 项视觉 fixture 能生成完整审核包。
- “昨日大事”全部既有测试保持通过。
- 两个 Skill 的完整测试、Skill 验证器、Python 语法和 `git diff --check` 全部通过。

人工验收使用包含 5 个项目的完整视觉 fixture，检查手机阅读节奏、标题吸引力、开头、项目区块、图片、结尾和微信编辑器粘贴效果。单项目 fixture 只用于边界测试，不得再作为最终视觉验收样本。

## 发布边界

两个 Skill 只生成本地研究包和微信公众号审核包。不得保存公众号凭证，不得登录后台，不得上传图片或文章，不得创建草稿，不得点击发布。
